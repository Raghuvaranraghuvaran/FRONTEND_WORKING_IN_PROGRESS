Implementation Plan
AI-Assisted Return-Fraud Detection E-Commerce Platform (India, COD-focused)
1. Background & Problem Statement
Indian e-commerce sees return fraud rates far above global averages, driven mostly by Cash-on-Delivery (COD)
orders, which have almost no verification at the point of purchase. The most common patterns are:
• Wardrobing — buying clothing (often ethnic wear) for a wedding/festival, using it once, then returning it
• Empty-box returns
• Serial over-ordering — ordering multiple sizes/variants with intent to keep one and return the rest
Enterprise fraud-detection tools exist but are priced for large retailers, leaving small-to-mid D2C brands ($50K–
$5M revenue) with COD checkout exposed and no affordable way to fight this.
2. Solution Summary
A full e-commerce platform — not just a fraud add-on — where fraud prevention is built into the core shopping
and returns flow. Every order and return is scored for risk in real time using the customer’s own order/return
history and passive device signals. High-risk actions require stronger verification before they’re allowed to
proceed. Low-risk customers experience zero friction.
3. Uniqueness of the Product
• COD-native fraud logic — most fraud tools are built for card/prepaid chargeback fraud; this is designed
specifically around India’s COD-heavy, low-verification checkout reality.
• Seasonal/cultural signal awareness — ties wardrobing detection to wedding/festival timing, auto-
tightening risk thresholds during those windows, a pattern generic global fraud tools don’t model.
• Passive-first device signals — lightweight device identification establishes trust without asking the
customer to do anything extra.
• Logistics-anchored return proof — trust is anchored in the delivery partner’s witnessed pickup rather than
customer self-attestation, which is far harder to game.
• Frictionless by default — low-risk customers are auto-approved instantly; step-up verification (SMS OTP,
bank-account validation) is reserved for risk-flagged actions only.
• Affordable for small D2C brands — designed for merchants who can’t justify enterprise fraud-tool pricing.
4. Two User Personas
Shopper
Register/sign in, browse by category, order (COD or prepaid), track orders, request returns, complete step-up
verification when required.
Merchant (admin)
View flagged orders/returns, view customer risk profiles, approve/reject flagged cases, see fraud trends.

8. Verification State Machine (Order/Return)
An order or return request is initiated by the shopper. The system first runs passive scoring using device
identification and order/return history signals, producing a Low, Medium, or High risk classification.
• If the classification is Low risk, the order or return is auto-approved immediately, with no further steps.
• If the classification is Medium or High risk, step-up verification is triggered: an SMS OTP is sent to the
customer’s registered mobile number.
– If the OTP is confirmed, the system proceeds to a risk-scoring pass that incorporates the verification
outcome before reaching a final approve/reject decision — verification does not bypass this step.
– If the OTP is not confirmed or is unavailable, the case escalates along one of two paths depending on
context: repeat or high-risk accounts are routed to bank/UPI penny-drop validation plus a prepaid-
only restriction going forward; returns are routed to mandatory doorstep-witnessed proof and the
manual review queue.
Every verification event is tagged with a verification_method (device_only / sms_otp / bank_validated /
doorstep_proof) so the risk engine can weight it by confidence level in later scoring.
Note: seasonal (festival/wedding), delivery-agent/route, and device-reuse signals are not separate decision
branches — they are all inputs into the single passive-scoring step described above, which is what produces the
Low / Medium / High risk classification.

12. How It Works — End-to-End Flow
Shopper Flow
The shopper signs up (email or Google). Passive device identification starts silently in the background, requiring
no action from the shopper. The shopper browses the catalog, adds items to cart, and checks out using COD or
prepaid. The risk engine scores the order using order/return history, device signals, and seasonal signals. A low-
risk order is placed instantly with zero friction. Later, if the shopper requests a return, the delivery partner
captures proof at doorstep pickup (a geo-stamped digital signature and a barcode/QR scan) rather than relying
on the shopper’s own attestation. A medium-risk return triggers an SMS OTP sent to confirm it’s genuine. If
confirmed, the return is approved and the shopper is notified by SMS or in-app message. If not confirmed, or if
the case is high-risk, it escalates to a bank/UPI penny-drop check and manual review, and the shopper is notified
of the outcome once a decision is made.
Merchant Flow
The merchant signs up, creates their store (tenant), and receives an API token. Once the storefront is live, every
order and return is scored automatically. Low-risk cases auto-approve with no merchant action needed. Flagged
cases land in the Flagged Queue, visible from either the dashboard or the browser extension. The merchant
opens a case, reviews the risk score, the customer’s risk profile, and delivery-agent risk context if relevant, then
approves or rejects it. The action is logged in the audit trail along with who took it and when. Over time, the
dashboard surfaces rule-weight tuning suggestions based on which auto-approved cases turned out risky versus
which flagged cases were cleared on review; the merchant chooses whether to apply or ignore each suggestion.
Chrome Extension Flow (quick triage)
The merchant installs the extension and enters their API token in Settings, which scopes the extension to only
that merchant’s tenant data. The toolbar badge shows a live count of pending flagged items, and a desktop
notification fires when a new high-risk order or return is flagged. Clicking the badge opens a popup showing the
flagged queue, where the merchant can approve or reject with one click — using the same audit trail and risk
data as the full dashboard.
13. System Architecture
High-level shape of the system, tying together the components described in the sections above.
Frontend layer
A single React.js application serves both the shopper-facing storefront and the merchant-facing admin
dashboard as separate route trees within the same codebase (or as two separate React apps sharing a
component library, depending on team preference). The frontend talks to the backend exclusively through the
Django REST Framework API — no direct database access from the client.
Backend layer
A Django + Django REST Framework application, organized into the app modules described in Phase 2: accounts,
catalog, orders, returns, fraud, and the admin dashboard API surface. All requests pass through a tenant-scoping
middleware that resolves the merchant_id for the current request (from the authenticated user or API token)
and makes it available to every view and query for that request.

--- Page 8 ---
Data layer
A single shared PostgreSQL database holds all tenant data, with merchant_id scoping enforced at the application
layer via the middleware above. Object storage (S3-compatible) holds doorstep return-proof records and any
device-session data that doesn’t belong in the relational database.
Risk-scoring layer
The fraud app sits alongside the orders and returns apps as an internal service: whenever an order is placed or a
return is requested, the relevant app calls into the fraud engine synchronously to get an initial risk classification
before the request completes. Follow-up scoring (after OTP or bank verification completes) happens through the
same engine, triggered by webhook/callback from the verification provider or by the frontend polling for status.
Asynchronous/background processing
SMS OTP dispatch, bank/UPI penny-drop calls, and customer notifications are handled as background jobs (e.g.,
via Celery with a Redis or database-backed queue) so the checkout and return-request endpoints stay fast and
don’t block on third-party API latency.
Integration points
• SMS/OTP provider (e.g., MSG91, Twilio, 2Factor) — step-up confirmation and customer notifications
• Payment gateway / bank-verification provider (e.g., Razorpay, Cashfree) — penny-drop validation
• Festival/wedding calendar data source — feeds seasonal threshold auto-tightening
• Google OAuth — shopper sign-in
Merchant-facing surfaces
The admin dashboard (part of the React frontend) and the Chrome browser extension both consume the same
admin API endpoints, scoped by the merchant’s API token, so there is a single source of truth for flagged queue
state, risk profiles, and audit history regardless of which surface the merchant uses.

ADDENDUM — Flaw Remediation & Revised Design
(Reserve Implementation Plan)
The section below supplements the Implementation Plan above with corrections identified in review. Where the
two disagree, this addendum represents the corrected/updated approach.
1. Risk Signals Are Too Simplistic → Weighted, Contextual Scoring
Replace raw counters with rate-based, time-decayed, combined signals. The COD refusal rate should be
calculated as refusals divided by total COD orders in the trailing 90 days, not a lifetime count. Return rate should
be tracked per category, since a customer who returns 40% of ethnic wear but 0% of electronics is a different
case than someone who returns everything. Return timing should be scored relative to category norms — a
wedding-outfit return on day 6 is a different signal than one on day 1.
Hard rule: no single signal (device reuse, festival timing, one refusal) can independently push a case to reject or
high-risk-block. Every signal is a weighted input into a composite score, and a minimum of two independent
signal categories must agree before an account is auto-restricted.
2. Verification Treated as Proof → Verification Is a Risk Modifier, Never a Bypass
SMS OTP and bank/UPI validation confirm who the account belongs to, not whether this specific return is
legitimate. Verification status should no longer determine approval directly. A verified identity reduces the risk
score by a bounded amount — enough to move a high-risk case down to medium, never straight to auto-
approve. Manual review remains reachable for any case above the high-risk threshold, regardless of verification
outcome.
3. State Machine Logic Problem → Verification Feeds Back Into Scoring, Doesn’t Bypass It
The corrected flow: an initial risk score is computed from passive signals. Based on that score, the appropriate
verification step is triggered (none, OTP, or bank/UPI). The verification outcome and its confidence level are
then combined with the initial score to produce an updated risk assessment, which is what the decision engine
actually acts on. The previous design let a confirmed OTP flow straight to approval; the corrected design always
recomputes a score after verification and routes it through the same decision engine, so verification changes the
inputs to the decision rather than skipping the decision itself.
4. Device Signal Collection Needs Reduction
Passive signal collection for the MVP should be limited to account age, order/return history, address consistency
across orders, a lightweight device-reuse identifier (a client-generated token stored via cookie/local storage, not
any form of device fingerprinting library), and payment method pattern (COD vs prepaid mix). Any more invasive
session-level tracking is deferred to a later phase, gated on demonstrated value over this reduced signal set, a
documented DPDP-compliant consent flow, and a defined retention/deletion policy.
5. Return Reasons Underused → Structured Taxonomy Feeding the Risk Engine
The return reason field should be constrained to a fixed set of values: wrong size, changed mind, damaged
product, wrong product received, missing item or component, quality issue, not as described, or other. Each
reason carries a base risk weight and interacts with category — wrong size on ethnic wear during wedding
season scores differently than wrong size on daily-wear basics, and changed mind on a high-value item from a
first-time customer scores higher than damaged product from a repeat, low-risk customer.
6. Delivery-Agent Collusion → Baseline-Adjusted Anomaly Detection, Not Accusation
Replace a raw "return rate per agent" metric with an expected-versus-actual model: the expected return rate for
an agent is the baseline return rate for their route/pincode/category mix, and the anomaly score is the gap

--- Page 10 ---
between actual and expected. Only a sustained, statistically meaningful deviation — with a defined minimum
sample size, such as 30 deliveries, over a rolling window — surfaces the agent in a review queue. That queue is
explicitly labeled an investigation signal, never a confirmed-collusion finding, and no automated action (such as
removal from doorstep-proof duty) happens without human sign-off.
7. Self-Tuning Underspecified → Recommendation-Only, With Governance
Self-tuning threshold suggestions are read-only in the first release: the dashboard shows suggested changes, but
nothing auto-applies. A suggestion only appears once a minimum sample size (e.g. 50 outcomes per rule since
the last change) and a minimum evaluation window (e.g. 14 days) have been met. Every applied change is
logged with its before/after values, who approved it, and when, feeding the same audit log used elsewhere in
the system. A rollback option restores the previous threshold set in one step. Fully automatic, unattended
threshold adjustment stays out of scope until the platform has enough historical outcome data to validate the
suggestion engine itself.
8. Fraud Outcome Labels Too Coarse → Expanded Set
The three-value outcome field should be replaced with a richer set: auto-approved, confirmed fraud, suspected
fraud, legitimate return, logistics issue, merchant issue, insufficient evidence, and verification abandoned. This
distinction is what makes both the self-tuning suggestions (Section 7) and the delivery-agent anomaly detection
(Section 6) trustworthy — thresholds can’t be tuned on outcomes that don’t separate "this was fraud" from "the
courier lost the item."
9. Data Model Too Simplified → Normalize History, Don’t Overwrite It
The order’s items should be broken out into their own records (an OrderItem per line, holding product, quantity,
and price) rather than a single combined field. Each risk-scoring event should be preserved as its own historical
record — including the score, tier, which rule version produced it, and which signals were used — rather than
overwriting a single risk_score field on the order or return. Each verification attempt (device-only, SMS OTP,
bank-validated, or doorstep proof) should likewise be preserved as its own event record with its method, status,
and confidence weight, rather than collapsing verification history into a single status field. Returns should be
broken into individual return-line records so partial-order returns are representable, and a timeline of return-
related events (requested, pickup scheduled, doorstep proof captured, OTP sent, OTP confirmed, escalated,
reviewed, decided) should be kept for each return request. Preserving this history — rather than repeatedly
overwriting a handful of summary fields — is also what makes rule versioning possible, since you can trace
exactly which threshold set produced any historical score, which the self-tuning audit trail in Section 7 depends
on.
10. Extension Auth Is a Security Risk → Least-Privilege, Short-Lived, Revocable
The long-lived static API token pasted into the extension’s settings should be replaced with a short-lived token
(for example, valid for one hour) that refreshes through a login flow rather than being permanently stored as a
secret. The extension should operate under a scoped role — able to read the flagged queue and risk views, and
approve or reject cases — but without full merchant-admin API access. Every extension request should be re-
authorized server-side against the merchant’s tenant, rather than trusting the client-held token alone. High-
impact actions taken from the extension, such as approving or rejecting a high-risk case, should require a
confirmation step rather than resolving instantly on a single click. The merchant should be able to revoke all
extension sessions from the main dashboard at any time.
11. Multi-Tenant Isolation Needs a Database-Level Boundary
The existing merchant_id middleware scoping should be kept, but backed by PostgreSQL Row-Level Security
policies on every tenant-scoped table, keyed off a per-request session variable identifying the current merchant.
This means that even a missing or incorrect merchant_id filter in application code cannot leak another tenant’s

--- Page 11 ---
rows — the database itself refuses to return them. Automated authorization tests that specifically attempt
cross-tenant reads, and assert they return nothing, should be part of the standard test suite.
12. MVP Scope Too Large → Trimmed First Release
The first release should include only the core storefront (catalog, cart, checkout for COD and prepaid, order
history), the reduced-signal risk scoring described in Section 4 above, SMS OTP step-up, doorstep QR/barcode
proof capture (without bank/UPI validation), and the merchant review dashboard (flagged queue,
approve/reject, audit log). Bank/UPI penny-drop validation, delivery-agent anomaly detection, self-tuning
suggestions, and the Chrome extension should all be deferred to a later phase, so the core fraud workflow can
be validated with real merchant data before adding surface area that’s expensive to secure and hard to justify
without evidence it helps.

Project Briefs
AI-powered return-fraud detection for Indian D2C e-commerce brands
Problem Statement
E-commerce platforms in India face return fraud rates far higher than global averages, driven heavily by
Cash-on-Delivery (COD) orders where customers order, refuse delivery, or return items after use with
almost no verification at the point of purchase. D2C brands and mid-market sellers lose heavily to
wardrobing (wearing and returning clothes after a wedding or festival season), empty-box returns, and serial
over-ordering (ordering multiple sizes with intent to keep one and return the rest). Enterprise fraud tools are
priced for large players, leaving smaller D2C brands with no affordable way to fight this.
Solution
A lightweight application for Indian D2C brands that analyzes each return or refusal risk in real time. It
factors in COD refusal history, return frequency per customer, address-mismatch patterns, and seasonal
wardrobing signals (e.g. ethnic wear returned right after wedding season), using the merchant's own order
data. Low-risk returns get auto-approved instantly to keep customer trust high; high-risk ones get flagged for
manual check or a small verification step such as photo proof or video unboxing requirement. Pricing is a
small percentage of fraud losses actually prevented, making it a zero-upfront-risk pilot for a small D2C
brand to try.
Solution Overview
A simple standalone application that receives a merchant's order and return data, looks at each customer's
order and return history, and gives every return request a risk score in real time. Low-risk returns get
approved automatically. High-risk cases (repeat over-orderers, COD refusal patterns, returns right after
festival season) get flagged for a quick manual check or a photo/video proof step before refund.
Target Users & Problem Fit
Small-to-mid Indian D2C brands ($50K-$5M revenue range) selling through their own e-commerce
operations with COD checkout. They lose real money to return fraud every month but cannot afford
enterprise fraud tools built for large retailers. They will use it because it is cheap to try (pay only a
percentage of fraud actually caught) and does not add friction for honest customers.

--- Page 2 ---
ReturnGuard
Technical Approach
Stack: Python backend, merchant order/return data integration, a risk-scoring model (starts rule-based, can
upgrade to ML later), and a simple merchant dashboard. Four key pieces: (1) order/return data ingestion,
(2) risk-scoring engine, (3) merchant dashboard showing flagged returns and savings, and (4)
auto-approve/flag decision logic wired into the merchant's return flow.
Team & Build Plan
One team member builds the merchant data integration first. Another builds the risk-scoring logic in parallel
using a small sample dataset. Once both are working, we connect them into a basic dashboard (built third),
then test on one pilot merchant's real historical data before demo.
Impact & Edge
Merchants keep more revenue without punishing honest customers with strict return policies. Unlike
enterprise fraud tools priced for large retailers, this is built cheap and specific to Indian COD/return
patterns—a gap the project aims to address for small D2C brands.

5.4 Never Trust the Frontend Payment Message Alone
Even if React shows a “Payment Successful” message, Django must not mark a payment as paid from that response
alone. The gateway’s signed webhook is the single source of truth — this prevents forged payment-success requests
from being sent directly to the API.

Final Result
This blueprint provides a complete backend direction: the current commerce and return-fraud platform, a dedicated
payment gateway / webhook / invoice / notification layer, and future bank/UPI validation, delivery-agent risk analysis,
analytics, threshold suggestions and a future browser-extension client. The visual frames and flow diagrams are
designed to make the implementation sequence easier to follow when using the document as a build specification.
